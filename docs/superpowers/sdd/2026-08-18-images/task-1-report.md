## Decisions

1. **Constructor takes `db: DatabaseExecutor`, not a no-arg constructor.** The brief's test sketch calls `new DrizzleMediaRepository()`, but every existing repository in this codebase (`DrizzleFollowRepository`, `DrizzlePostRepository`, `DrizzleUserRepository`, etc.) takes `constructor(private readonly db: DatabaseExecutor)`, with tests doing `new DrizzleFollowRepository(db)`/`new DrizzlePostRepository(db)`. There's no default-export `db` pattern anywhere for a no-arg constructor. Since the brief's own "resolutions" section already establishes that the test sketch needs adaptation (helpers didn't exist and had to be written locally), and the "Patterns to follow" instruction pointed explicitly at `drizzle-follow.repository.ts`/`.test.ts` for repository style, I followed that established pattern instead of the sketch's literal no-arg call: `const repo = new DrizzleMediaRepository(db);` in the test file. This keeps `DrizzleMediaRepository` composable inside a transaction the same way every other repository is (see `DatabaseExecutor`'s own docstring about unit-of-work composition), which a no-arg constructor would have foreclosed.
2. **`listForPost`/`listForPosts` order by `position`.** The port docstring doesn't specify an order for these two, but `claim`'s docstring says `position` is "the index in `ids`" and the brief's own test asserts `listForPost` returns rows in claim order — so I ordered both by `position` ascending. This is untested for `listForPosts` specifically (no test exercises the multi-post batch method at all in this task — it's plumbing for a later task), so it's a reasonable-but-unverified choice.
3. **`findManyByIds` has no ordering guarantee** — not specified by the port and not exercised by any test in this task; returns whatever `inArray` yields.
4. Empty-array short-circuits in `findManyByIds` and `listForPosts` (`if (ids.length === 0) return []`) avoid handing Drizzle's `inArray` an empty list, which is unsound at the SQL level. Untested here (no test calls either with an empty array) — flagging this as unverified defensive code rather than a proven contract.

## Unsure about

- Whether `listForPosts` and `findManyByIds`'s exact behavior/ordering will matter to a later task that actually exercises them — flagged in "Decisions" above so a reviewer can weigh in before those are load-bearing.
- The constructor-signature deviation from the brief's literal sketch (point 1 above) is the one place I diverged from the brief's exact code rather than its exact values (table/column/index names, types, nullability) — I believe this is the correct call given the codebase-wide pattern, but it's a judgment call worth a second look.
