# Migrations

Generated by `bun run db:generate` from `src/db/schema.ts`. Never hand-write migration SQL,
and never edit a migration that has already been applied anywhere — drizzle records each
applied file's hash in the `drizzle.__drizzle_migrations` **table**, so an applied file that
changes will not re-run, and the edit silently diverges from what the database actually has.

Apply with `bun run db:migrate`.

## Known hazard: `0003_romantic_rattler.sql` requires an empty `community` table

```sql
ALTER TABLE "community" ADD COLUMN "slug" varchar(120) NOT NULL;
```

`ADD COLUMN ... NOT NULL` with no `DEFAULT` and no backfill **fails outright** if the
`community` table already has rows:

```
ERROR:  column "slug" of relation "community" contains null values
```

### Why this is not fixed by a new migration

A later migration cannot help. Migrations run in order, so `0004` never executes in an
environment where `0003` aborts — the fix would have to be inside `0003`, which is already
applied and must not be edited. The two available responses are therefore "confirm no
environment can hit it" or "hand-repair the affected database before migrating". This
repository takes the first, on the following evidence (checked 2026-08-08):

- `main` contains no *application* code path that inserts into `community` — the repository,
  use-cases and routes all arrive on `phase-2-auth-community`. **It does not follow that the
  table is empty.** `main`'s own schema tests insert into `communities`
  (`apps/api/src/db/schema.test.ts`), and those tests clean up in `beforeEach` only, with no
  `afterEach`/`afterAll` — so rows survive a completed run. The realistic trigger needs no
  hand-written SQL at all: run `bun test` on `main`, check out this branch, run
  `bun run db:migrate`, and `0003` fails with
  `column "slug" of relation "community" contains null values`.
- There is no deployment: `infra/` contains only the local `docker-compose.yml` for
  Postgres, and the repository has no CI or deploy configuration. The only databases in
  existence are developer machines and ephemeral test databases.
- The local development database was verified empty
  (`select count(*) from community` → `0`) before `0003` was applied.

### If you do hit it

Almost always the rows are leftover test data, and the fastest correct fix is to drop the
local volume and start clean:

```bash
docker compose -f infra/docker-compose.yml down -v
docker compose -f infra/docker-compose.yml up -d
cd apps/api && bun run db:migrate
```

Only if the rows are data you actually want to keep, give them a slug by hand and then let
the migration run:

```sql
ALTER TABLE community ADD COLUMN slug varchar(120);
UPDATE community SET slug = 'komunitas-' || left(id::text, 8) WHERE slug IS NULL;
ALTER TABLE community ALTER COLUMN slug SET NOT NULL;
ALTER TABLE community ADD CONSTRAINT community_slug_unique UNIQUE(slug);
```

then re-run `bun run db:migrate` — drizzle-kit will see the columns already exist and record
`0003` normally.

**Do not hand-edit `meta/_journal.json` to mark `0003` applied.** Drizzle tracks which
migrations have run in the `drizzle.__drizzle_migrations` **table** (hash + timestamp per
migration); `_journal.json` is the list of migrations to run and holds no hashes. Editing it
desynchronises it from `meta/*_snapshot.json` and breaks the next `db:generate`.

### For future migrations

Adding a `NOT NULL` column to a table that may hold rows takes three generated steps, not
one: add it nullable, backfill, then tighten. Reach for that shape whenever the table is
not provably empty.
